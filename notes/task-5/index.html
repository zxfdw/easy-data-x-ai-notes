02 这次的体会

1. 记忆的难点不在"存"，在"忘"——这句话我这次是亲手验证的。

写入太容易了：我往 PowerContext 里放 6 条，一次全进，没有任何阻力。但检索"回答风格偏好"时，它把"回答代码问题时先解释再给示例"也一并捞了回来，分数 0.032，跟正确的那条 0.033 几乎一样。

这两条都跟"回答"沾边，语义上确实近。可它们不是一类东西：一条是用户偏好（要什么风格），一条是行为规则（我该怎么答）。如果 Agent 把后者当前者用，就会拿一条操作规则去理解一个用户需求。所以我理解的"难的是忘"，不是说存储成本高，而是记多了以后，要能分清哪条该在这时候想起来——这需要分类、需要降权、需要过期策略，是设计问题。

2. File SQL 真正的价值在"零建表"，不在语法像 SQL。

这次我特意没有落任何持久表——read_csv 把文件当成语句级临时关系，查完就散。对照 Task 4 学的 I1，两件事的区别就清清楚楚了：I1 解决"数据长期存哪、怎么被四种方式查到"，I4 解决"一次性文件怎么不折腾地查掉"。文档里那句"扫描对象存储或跨节点文件 → 用专门的外表方案"划的就是这条线。我手上经常有团队导出的 CSV、检测报告表格，以前总想"建个表"，现在知道这种看一次的数据根本不该建表。

3. 安全不是附加项，是 File SQL 能不能用的前提。

I4 用一整节讲 Path Guard，我自己实现时才发现那条检查链一点不多余：如果不做路径规范化、目录边界、普通文件检查，/etc/passwd 这种路径就能被读进去。"只读"不等于"安全"——任意文件读取本身就能泄露密钥和配置。这条对我手上的研发知识库是直接相关的，不是理论。

4. 一个感受：越是"没有现成脚本"的任务，越能看出自己有没有真懂。

Task 5 的两个部分都没有配套代码——P3 是课程稿，I4 是设计文档。我得自己把"五步闭环"和"三类记忆"落成能跑的东西，跑通了才算数。这个过程中我发现，光"读过"和"能实现"之间差得很远：读 P3 时觉得三类记忆挺清楚，真写的时候才要想"哪类记忆该走哪种检索"。

5. 对研发场景的直接启发。

研发知识库可以照这三类来分：事实（标准号、材料牌号、注册证号）走语义记忆；经验（某次试验为什么失败）走情景记忆；规则（评审流程、变更留痕要求）走程序记忆。三类分开存，检索时就不会串。另外 I4 给的那套 Agent 准则——先 glob 发现、再 DESCRIBE 看列、再 LIMIT 预览、最后才全量——可以直接写进我自己 Agent 的工具协议。
