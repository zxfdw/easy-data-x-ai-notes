读法： 混合检索在召回（recall +0.10、precision +0.075）上明显更好，但在忠实度（faithfulness −0.02）和答案相关度（answer_relevancy −0.018）上略低。也就是说——混合检索"找得更全"，但找回来的东西多了，模型更容易说一点不在证据里的话。

02 这次的体会

1. "该不该查"和"查得准不准"，是两件完全不同的事。

d3_2 里最能说明问题的是第 4 个问题——"今天天气怎么样"。我给这个问题的预期是"不需要检索"，Agent 确实没有去翻知识库，而是直接说明自己只答产品技术问题。对比 d3_3 里那些"检索了但答歪"的场景，我意识到这是两种不同的失败：一个是不该查却查了，一个是查了但没查对。Agentic 这一层管的是前者，混合搜索管的是后者。以前我笼统地觉得"RAG 效果不好"，现在知道要先分清是哪一种。

2. "增强检索 3/5 优于纯向量 1/5"，但这不是"更好"的意思。

d3_3 把五个场景摆在一起跑，能看出增强检索并不是万能药：场景二（Q3 营收）两种方式都答错了，场景五（纯语义）增强检索反而更差。这跟 Task 4 里 d2_4 的结论对得上——混合搜索补的是"另一条判断路径"，不是"精度升级"。它救的是那些"字面精确"的查询（错误码、函数名），救不了纯语义查询的跑偏。

这一点在 RAGAS 的分数里也能看出来：混合检索召回更好（0.883 vs 0.783），但忠实度反而略低（0.899 vs 0.919）。找回来的多了，模型说跑题话的机会也多了。所以"召回"和"忠实"是要权衡的，不是一起涨。

3. 生产环境的三个变量，都不是模型问题。

d3_4 演示的三件事——工具描述质量、top_k 取值、增量更新——全都是"工程配置"层面的事，跟模型能力无关。工具描述写模糊时，模型自己把查询扩写成"OceanBase 4.2.1 版本兼容性问题"；写清楚时就直接写"OB-4.2.1 版本兼容性"。这跟前面几课反复出现的那句话对上了：Agent 能力 = 模型能力 × 数据质量 + 流程编排——这次三件事全落在"流程编排"里。

4. 换成自己的 API 后，才知道课程代码里有多少默认假设。

这次我把整个 D3 都跑在阿里云 DashScope 上（而不是课程默认的模型）。过程中改了三处：模型名要写成课程环境里的可用模型；评测用的 embedding 要关掉一个默认行为才能兼容阿里云的接口；还有一个评测依赖的版本要对齐。这三处都不是我写错了代码，是课程默认环境和我的实际环境不一样。体会是：跑开源项目时，"跑不通"经常先要判断是环境问题还是代码问题，而不是直接改代码。

5. 对研发知识库的直接启发。

这套东西我准备这样用：先分清失败类型再改（是不该查、还是没查对）；别指望一个检索策略包打天下，字面精确和语义理解要分开看；工具描述要当代码来写，因为那直接决定 Agent 怎么用你的系统。
