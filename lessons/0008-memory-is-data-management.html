Easy Data × AI · 第 8 课（对应 Task 8 · D4 + I7）

存下来容易，管起来才难

学完这一课，你能把一个"会记忆的 Agent"从"能存能取"推进到"能隔离、能压缩、能分层、能清理"——并知道工业实现把这些拆成了哪些接口。

  • 预计耗时 14 分钟
  • 关联 d4_1 ~ d4_8
  • 类型 概念 + 实测 + 工程

先接上一课的话头

第 5 课讲记忆系统时留了一句判断：写入极容易，检索才是难点。D4 这次干脆把整件事拆成八个脚本，一个个跑给你看：先跑"能存能取"，再跑"存了之后怎么管"。

记忆系统的工程量，几乎全在"记住之后"。存进去是一行代码的事；隔离、压缩、分层、清理，才是要设计的地方。

先看差距：有没有记忆，体验差在哪

d4_2 和 d4_3 是一组对照。同样四轮对话，差别在第四轮暴露得最彻底。

版本第一轮用户说第四轮的表现
d4_2 无记忆我是 Python 开发者，喜欢简洁回答"作为 AI 我无法跨会话记忆昨天的对话内容"，用户被迫重新自我介绍
d4_3 有记忆同上，Agent 存入 3 条记忆记得身份与偏好，推荐直接落到"Python 后端 + 简洁"口径

d4_3 跑完，记忆库里有 5 条：身份两条、偏好一条、项目需求两条。差别不在模型，在有没有把这两句"记住"。

重头戏在 d4_5 ~ d4_8

如果说 d4_1~d4_3 是"能不能用"，d4_5~d4_8 就是"能不能上生产"。

脚本管什么关键结论
d4_5 多用户隔离记忆不能串到别人身上用 user_id 做命名空间，在查询构建阶段就过滤
d4_6 压缩记忆会越存越多"多条变一条"换压缩比；画像承载稳定约束，事实库承载长尾
d4_7 冷热分层热索引不该被冷数据拖累冷数据必须移出热索引，不能只靠排序沉底
d4_8 清理该忘的必须忘掉三级处置 KEEP → ARCHIVE → DELETE；硬删要级联主库/向量/缓存

d4_5 那条最值得记：过滤要发生在"查询构建阶段"，而不是"检索完之后再丢弃"。检索后再丢，等于先把别人的数据取出来再扔掉——既浪费又危险。这类"看起来等价、实则不等价"的实现选择，是分水岭。

I7 想讲的，是把 D4 放到工业尺度上看

I7（PowerContext 的设计与实现）目前在课程里还标着"开发中"，但它列出的方向已经把边界划清楚了：

  1. 数据关系：Source、Memory、PreparedContext、Handoff 四者怎么串起来
  2. 可追溯：不可变修订、证据引用、生命周期管理
  3. 接口边界：Server、Client、Core SDK、HTTP、MCP 各管一段
  4. 检索契约：全文、向量、混合检索各自的约定

D4 是"我从零搭一遍，看懂原理"；I7 是"工业实现怎么把它拆成可替换的接口"。一个讲原理，一个讲边界。

接到你的实际场景

把这一课接到自己的 AI 工作流上：

  1. 先分清"记忆"和"知识"。 知识是相对稳定的文档，记忆是不断写入、还要忘掉的数据。两者都要管，但管理方式不同。
  2. 多用户场景，隔离是第一条红线。 任何带用户标识的记忆，检索时都要带上那条过滤条件，而且是在查询里带，不是查完再扔。
  3. 记忆要设计"生命周期"。 别只想着怎么存，先想清楚什么该 KEEP、什么该 ARCHIVE、什么该 DELETE。
  4. 报错先分环境还是代码。 版本冲突、权限、模型名这三类，又占了"跑不通"的一大半。
