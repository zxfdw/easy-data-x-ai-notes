Easy Data × AI · 第 9 课（对应 Task 9 · P5 + D5 + I8）

量不出来，就不算落地

学完这一课，你能把"AI 到底行不行"从一句感觉，拆成可定位的指标组、可对比的 ROI 情景，和一条可以直接拿去决策的盈亏平衡线。

  • 预计耗时 13 分钟
  • 关联 P5 离线评测 + ROI
  • 类型 概念 + 实测 + 决策

先接上一课的话头

第 5 课留的原话是"难的不是记住，是忘掉"；第 8 课把记忆从玄学拽回了数据管理。这一课更进一步：你搭起来的这套东西，到底好到什么程度、在什么条件下成立？

Agent 能不能落地，不取决于它演示时多惊艳，取决于你能不能稳定地量出它的效果、成本、延迟和失败率。

第一件事：把"AI 行不行"拆成四层指标

P5 的离线评测跑了 30 个样本，报告刻意分成四组指标——这个分法比一个笼统的"准确率"有用得多。

层指标实测值
数据层知识覆盖率 / 检索命中率 / 检索故障率82.76% / 95.83% / 3.33%
模型层回答准确率 / 幻觉率96.67% / 3.33%
业务层任务成功率 / 转人工率 / 行为一致率73.33% / 23.33% / 100.00%
运行层工具成功率 / 平均延迟 / 平均 Token80.00% / 108.67ms / 23.53

注意这组数里最有意思的地方：检索命中率 95.83%，任务成功率却只有 73.33%。差的 20 多个点，不是"模型不行"，是被转人工、缺知识、工具失败这些具体环节吃掉的。能定位到环节，才知道该改哪里。

第二件事：用 ROI 三种情景，把话说圆

同一套假设，乐观、悲观、基准各算一遍：

情景净收益ROI回收期盈亏平衡
conservative-3,644 元-24.46%107.89 月115 单/月
base+9,200 元67.65%3.64 月52 单/月
optimistic+25,784 元188.92%1.61 月37 单/月

保守情景亏钱，反而是这套模型可信的地方。当业务量不够、转人工率高、单任务成本又高的时候，Agent 就是划不来的——这是实话，也是决策要看的。三个情景都漂亮盈利，才该怀疑是不是在凑结论。

更值得盯的是最后一列"盈亏平衡任务量"：它比 ROI 更直接地回答"我们要做到多大规模，这套东西才值得上"。ROI 是结果，盈亏平衡点是可以拿去对齐目标的门槛。

第三件事：把"证据"做成可复现

P5 不只是跑出数字，还把整套链路留了下来：Agent API、Prometheus 指标、100 条 demo 流量、38 项单测。

  • run_eval 产出 JSON + Markdown 报告，30 条样本明细可逐条回溯
  • ROI 命令一次跑完三情景，落 markdown / json / csv 三种格式
  • unittest 38 tests OK，保证指标口径不被后续改动悄悄改掉
  • 100 条 demo 流量灌进 API，/metrics 上 agent_requests_total 正好 100

I8 想强调的"避免把单次演示或单个基准数字当成通用结论"，落点就在这里：记录输入、输出、执行轨迹，让结论可复现，而不是"我跑过一次，是对的"。

自测：三个问题

试着不看上面作答（提取练习比重读一遍有效得多）。

1. 检索命中率 95.83%、任务成功率只有 73.33%，这说明？

2. 保守情景算出来是亏钱的，为什么反而是好事？

3. 盈亏平衡任务量比 ROI 更适合拿去做什么？

提示三题答完再看反馈；答错比答对更有价值：说明那里正是你要补的。

接到你的实际场景

把这一课接到自己的 AI 工作流上：

  1. 先定义成功标准，再谈做不做。 一个 AI 需求提上来，先问"成功长什么样、怎么量"，而不是先问"能不能做"。
  2. 指标要分层。 数据层、模型层、业务层、运行层分开看，出问题才定位得到环节。
  3. 决策看门槛，不只看 ROI。 盈亏平衡任务量这种"要做到多大才划算"的数，比一个漂亮百分比更有用。
  4. 把证据留成可复现的。 报告、脚本、单测留在仓库里，别人能重跑出同样的数，结论才站得住。
