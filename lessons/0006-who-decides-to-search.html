Easy Data × AI · 第 6 课（对应 Task 6 · D3 + I5）

到底该不该查：Agent 自己说了算

学完这一课，你能分清 RAG 的两种失败：该查的没查和查了但没查对——前者交给 Agent 判断，后者交给检索配置。

  • 预计耗时 12 分钟
  • 关联 d3_2 / d3_3 / d3_4
  • 类型 概念 + 对照 + 工程

先接上一课的话头

第 4 课讲的是"同一份数据要有四种查法"——那是数据层的事：存的时候就把可查信息带全。

D3 换了个角度问：谁来决定要不要查？

前面所有 RAG 示例都有一个隐含前提——默认"每个问题都该去检索一次"。可真实用户会问"今天天气怎么样"。这时候还去翻产品知识库，就是浪费一次又快又贵的模型调用，答出来也是错的。

两种失败，各归各管

d3_2 和 d3_3 一起看，正好把 RAG 的失败分成两类：

失败类型例子该由谁负责
不该查却查了"今天天气怎么样" → 仍去检索知识库Agent 的判断（Agentic 这一层）
查了但没查对"E-4012 错误" → 捞回 E-4013检索配置（索引 / 混合搜索）

d3_2 里那个闲聊问题，Agent 没有去查库，而是直接说明自己只答产品技术问题。这正是 Agentic RAG 与普通 RAG 的分界——不是"会不会用工具"，是"自己判断要不要用一次"。

"1/5 → 3/5"，数字要连着看

d3_3 把五个场景摆在一起跑，结果是这样的：

场景纯向量增强检索看点
错误码 E-4012❌✅字面精确命中，混合搜索救回来了
Q3 营收数据❌❌两种都错，都倒回 Q1
版本号 OB-4.2.1✅✅纯向量就够（点号分词器不支持）
函数名 DBMS_HYBRID_SEARCH❌✅典型"必须找准"的查询
纯语义"优化查询性能"❌❌增强检索反而跑偏

汇总命中率是纯向量 1/5、增强检索 3/5。但真正该带走的不是"增强更好"，而是——

增强检索补的是"另一条判断路径"，不是"精度升级"。

场景五里它反而更差。把"增强"当"更好"用，就会在这种地方翻车。

三个生产变量，没一个是"模型问题"

d3_4 演示的三件事，全在工程配置层：

  1. 工具描述质量。 模糊描述时，模型自己扩写成"OceanBase 4.2.1 版本兼容性问题"；清晰描述时直接写"OB-4.2.1 版本兼容性"。描述怎么写，决定了 Agent 怎么用这个工具。
  2. top_k 取值。 1 → 3 → 5 → 8，是拿召回数量换精度。调大不一定更好。
  3. 增量更新。 知识库要能持续长——写入 1 条后从 19 条变 20 条。

对应到 Task 1 写下的那句公式：Agent 能力 = 模型能力 × 数据质量 + 流程编排。这次三件事，全落在最后那个加号后面。

一个顺手的教训：跑不通 ≠ 代码写错

d3_2 和 d3_4 第一次跑都报 404，原因是脚本里写死的模型是 deepseek-ai/DeepSeek-V3，当前 Key 没这个权限。

先自己猜如果是你，下一步会先改代码还是先看报错？

改成课程一直在用的 qwen3.7-flash 就正常了。先看报错是不是环境（权限、模型名）问题，再去动代码——这条在跑任何开源项目时都省时间。

接到你的实际场景

把这一课接到研发知识库、注册资料、项目周报上：

  1. 别让 Agent 对每个问题都去查库。 有人问"这个项目负责人是谁"（结构化查询）、"上次会议结论是什么"（文档检索）、"今天有什么安排"（不需要查）——先判断类型，再决定查不查、查哪。
  2. 检索答歪时，先分清是哪种失败。 是不该查却查了（Agent 判断问题），还是查了没查对（检索配置问题）？两种的修法完全不同。
  3. 工具描述要当代码写。 你给 Agent 的工具描述，直接决定它生成的查询词。模糊描述 = 让 Agent 自己猜。
