Skill 与上下文工程

一页纸：Skill 的四要素、碎片化的三层、Skill 检索与 RAG 的对应、Skill 何时升级成 MCP 工具。

Skill 的四个必备要素

要素作用反例
命名稳定、具体、可检索，供系统索引与路由helper、docs、我的超强技能
描述写清适用任务、触发场景、边界范围"帮助写 API 文档"（太宽，不知何时该用）
输入区分必填 / 可选，说明来源全写成"最好有"，Agent 不知何时该追问
示例最小样例校准行为与边界只堆材料，不给"该拒答"的例子

精神与 MCP Tool 一致：稳定名称做识别，清晰描述做触发，结构化参数做约束，示例校准行为。缺了这四样，Skill 就退化成一段散文——人读着有感觉，Agent 用起来不稳定。

碎片化的三层与对应解法

层面表现数据视角的解法
项目隔离项目 A 的规则，开新项目要手动搬把 Skill 当数据资产管理：
统一存储 → 索引 → 语义检索 → 跨工具/项目/团队共享
工具隔离Cursor / Claude Code / Copilot 格式互不兼容
人员隔离同事的好规则只能手动粘贴，各自分叉

根因对照：知识库分散 → RAG 检索不到 → AI 答不好；Skill 分散 → Agent 找不到最佳技能 → 行为不专业。同一类问题。

Skill 检索 ≈ RAG（复用同一套机制）

维度RAG（P2）Skill 检索（P4）
检索对象知识文档技能文档
机制语义相似度召回语义相似度召回
混合检索必要"npm 包" 别召回 "Python 包"精确匹配关键词的那部分同样重要
Agentic 判断要不要搜 / 搜哪里 / 够不够好这次请求要不要调 Skill

记住一句知识库管"事实数据"，记忆系统管"用户数据"，Skill 库管"经验数据"——底层都是存储、索引、检索、更新。

Skill → MCP Tool：什么时候升级

阶段形态适合场景
快速迭代Skill 文档（SKILL.md）流程还在天天改，先写文档最灵活
稳定 + 跨端复用MCP Tool（Server 暴露）输入稳定、输出可结构化、要被多客户端统一调用

升级判据：不是"写得越早越好"，而是"足够稳定" + "需要被统一发现和调用"。X5 的 review_code_diff 就是 code-review Skill 的 MCP 化结果。

上下文工程三条红线

  1. 不是塞得越多越好。 上下文是有限资源，全量注入 ≠ 效果更好（X2：按需加载省 ~76%）。
  2. 先分清职责边界。 Source / Memory / PreparedContext / Handoff 各管一段，别混在一起。
  3. 跑不通先分环境还是代码。 版本冲突、权限、模型名，占了"跑不通"的一大半（本次 PowerContext 的 openai 版本冲突、X5 的 mcp 大版本差异都是这类）。
