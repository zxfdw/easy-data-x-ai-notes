记忆系统与 File SQL

一页纸：三类记忆的分工与缺失判断、记忆读写的两种模式、File SQL 五步闭环与安全红线。

三类记忆

类型存什么类比举例
语义事实和知识百科全书"用户是 Python 开发者"
情景过去的经历日记本"上次用 Docker 方案解决了部署问题"
程序行为规则操作手册"回答代码问题时先解释再给示例"

诊断口诀：Agent"不够懂我"时先问缺口——不记得事实（语义）？不记得经验（情景）？不懂规矩（程序）？三种缺失，三种修法。

唯一可自我修改的是程序记忆——这就是"从反馈中学习"的机制，也是下一期 Skill 的前身。

写入与读取

环节模式好处代价
写入实时：对话中主动判断透明，用户可感知占用对话推理资源
异步：结束后后台提炼不干扰体验写入有延迟
读取检索把"想起来"变成一次检索问题检索不准 = 记忆等于没有

⚠️ 实测教训：写入极容易，检索才是难点。我写入 6 条后查"回答风格偏好"，把程序记忆（怎么答，0.032）和语义记忆（要什么，0.033）一起捞了回来——分数几乎一样，类别却完全不同。所以"忘"（降权、过期、分类）比"记"更考验设计。

File SQL 五步闭环

步骤函数要点
1 发现glob只列路径不读内容，不猜文件名
2 描述DESCRIBE执行前确定列名与类型
3 查询read_csv(...)语句级临时关系，零建表
4 关联JOIN read_parquet(...)跨格式 JOIN，Reader 只产批次
5 导出COPY ... TO不覆盖、先临时后原子发布

为什么 Schema 必须在执行前确定？

客户端收第一行结果前就得知道有哪些列，所以文件扫描必须接入 SQL 的编译期与执行计划——这正是"Reader 与 SQL 引擎职责分离"的原因。

安全红线（Path Guard 检查链）

功能是否启用
  → secure_file_priv 是否配置
  → 路径规范化与 realpath
  → 是否位于允许根目录
  → 是否为普通文件
  → 以只读、安全标志打开
  → 对文件描述符再次校验

必须拒绝：.. 逃逸、前缀碰撞绕过、符号链接跳白名单、目录/FIFO/设备文件，以及"从数据库服务器读客户端本地路径"。

⚠️ 红线：只读 ≠ 安全。任意文件读取就能泄露密钥与配置。

何时用 / 何时别用

场景建议
临时查看上传的 CSV✅ 用 File SQL
两份本地中小文件做一次关联✅ 用 File SQL
数据要长期复用、索引、事务❌ 导入正式表
扫描对象存储 / 跨节点文件❌ 用专门外表/湖仓方案
复杂嵌套 JSON / Excel❌ 先专用工具预处理
