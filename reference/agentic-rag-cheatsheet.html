Agentic RAG 与 AI 列

一页纸：两种失败的分工、"增强"的正确用法、生产三变量、环境坑清单。做 RAG 时随手回看。

RAG 的两种失败

失败典型信号该由谁负责
不该查却查了闲聊问题也去翻知识库Agent 的判断（Agentic 层）
查了但没查对精确编号漂到同主题文档检索配置（索引 / 混合搜索）

Agentic RAG 与普通 RAG 的分界：不是"会不会用工具"，是"自己判断要不要用一次"。

"增强检索"不是"精度升级"

场景纯向量增强检索
错误码 E-4012❌✅
Q3 营收数据❌❌
版本号 OB-4.2.1✅✅
函数名 DBMS_HYBRID_SEARCH❌✅
纯语义"优化查询性能"❌❌ 反而更差

汇总：纯向量 1/5，增强检索 3/5。它救的是"字面精确"的查询（错误码、函数名、版本号），救不了纯语义跑偏。把它当"更好"用，就会在纯语义场景翻车。

生产三变量（都不是模型问题）

变量作用怎么调
工具描述决定 Agent 生成的查询词写清楚，别让模型自己猜
top_k召回数量换精度1 → 3 → 5 → 8，不是越大越好
增量更新知识库能不能持续长写入后条数随之增长

三件事全落在公式 Agent 能力 = 模型能力 × 数据质量 + 流程编排 的最后一项。

环境坑清单

  • 模型名写死。 课程脚本里写死 deepseek-ai/DeepSeek-V3，换 Key 后 404 → 改成自己 Key 可用的模型（如 qwen3.7-flash）即可。
  • 先看报错是不是环境（权限、模型名），再动代码——跑开源项目时"跑不通"和"写错了"经常不是一回事。
  • 异步索引。 写入后立刻查可能返回"无结果"，隔几秒重跑即正常（与 d2 同源现象）。

给 Agent 的工具协议

list_allowed_files(pattern)
  → describe_file(path, format_options)
  → preview_file(path, limit)      # 必须 LIMIT
  → query_files(sql)
  → export_query(sql, target)
  → verify_export(target)

准则：先发现再读取；先 DESCRIBE 再看列；先小样本再全量；文件变化/权限错误立即停，不自动放宽配置。
